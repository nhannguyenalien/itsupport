# AI Windows Support Agent — v0.1 Spec

Source of truth for scope. Captured verbatim from the scoping conversation — do not
expand scope without updating this doc first.

## Scope contract

**IN**
- Multi-tenant backend
- Secure device enrollment
- Go agent (Windows)
- 12 read-only tools
- 5 safe-action tools
- Policy Engine (4 levels)
- Approval workflow
- Ticket/chat UI
- MeshCentral takeover
- Kill switch
- Audit log
- AI orchestration
- Mandatory tool-based verification
- Metrics
- Demo scenarios A/B/C/D

**OUT** (explicitly deferred past v0.1)
- Browser automation
- Playwright/CDP
- Chrome extension
- Flutter
- Linux agent
- IoT
- Google/Meta Ads integrations
- CAD
- Arbitrary PowerShell execution
- Agent auto-update

## Why no `run_powershell`

> Linux only: free-form commands are proposed in [`v0.3-linux-shell-addendum.md`](v0.3-linux-shell-addendum.md)
> as a per-command classified `shell.run`. This rule still holds for Windows and macOS.

If the agent exposes arbitrary script execution, the Tool Registry, policy engine,
and approval workflow are theater — anything downstream of "run this script" is
unenforceable. The agent only exposes compiled, allowlisted actions. Flexibility
later comes from signed script *packages* the backend can invoke by name with
parameters — never free-form code from the model.

## Tool Registry (v0.1)

The scoping message enumerated 16 concrete tools. Splitting by whether the action
changes device state gives an 11 read-only / 5 write split, not the "12 read-only"
figure quoted in prose — **one read-only tool short of spec**. Flagging rather than
silently picking one: confirm the 12th read-only tool (candidates: a
`printer.driver_info`-style read, or `eventlog.list` distinct from `eventlog.read`)
before backend implementation locks `registry.json`. Until reconciled, the registry
ships with the 11 confirmed read-only tools below; write actions are exactly 5 and
match spec.

Read-only (11 confirmed, spec says 12) — auto-executed, no approval required:
- `service.status`
- `process.list`
- `network.ping`
- `network.dns_lookup`
- `disk.usage`
- `temp.scan`
- `printer.status`
- `printer.queue`
- `printer.test` *(read/verify only — triggers a test print but changes no config; treated as read-only for approval purposes, confirm this framing)*
- `system.info`
- `eventlog.read`

Write/safe-action (5) — require approval in v0.1 (no autonomous default):
- `service.restart`
- `process.kill`
- `network.flush_dns`
- `temp.clean`
- `printer.clear_queue`

Each tool registry entry carries:
```json
{
  "tool": "service.restart",
  "risk": "medium",
  "verification": ["service.status"]
}
```
Verification is deterministic and defined in the registry, not left to prompt
discipline. An action only reaches `RESOLVED` when every step in its
`verification` chain passes; otherwise `REMEDIATION_FAILED` and the AI may try an
alternative or escalate to a human.

## Enrollment flow

```
Admin creates enrollment token
  -> one-time token, 10 minute TTL
  -> Agent generates keypair locally
  -> Agent sends public key + token
  -> Server verifies
  -> Server issues device certificate
  -> Agent uses mTLS from then on
```

Day-one controls (must exist before pilot, not "later"):
- **Revoke Device**
- **Pause Device Actions**
- **Disable Tenant AI**

## Agent process separation (Windows)

Never run the whole agent as one SYSTEM-privileged blob:

```
support-agent
├── connection daemon     (low privilege)
├── telemetry             (low privilege)
└── privileged executor   (elevated)
```

The executor only accepts messages that pass signature/schema verification AND
whose `tool` exists in a compile-time allowlist. An unknown tool name (e.g. a
hypothetical `powershell.exec` from a compromised or buggy backend) is rejected at
the agent boundary — defense in depth even if the backend has a bug.

## Verification is deterministic, not vibes

"Looks fixed" from the model is never a terminal state. Concrete example:

```
service.restart("Spooler")
  -> service.status("Spooler") == RUNNING
  -> printer.test() == SUCCESS
  -> RESOLVED
```
Any failed check -> `REMEDIATION_FAILED`, not silent success.

## Data privacy (v0.1)

No raw dumps to the LLM. Orchestrator preprocesses first:

```
Event Log -> filter relevant events -> redact (username/path/email/IP per policy) -> LLM
```

`process.list` sends only `name, cpu, memory, status` — never full command line
(may contain tokens/passwords).

Per-tenant AI Data Policy (pick one):
- Standard
- Redacted
- No screenshots
- No raw logs

Enterprise tier (post-v0.1) may add private/local model option.

## Metrics (feature, not an afterthought)

Log from day one:
`tickets_total`, `tickets_ai_resolved`, `tickets_escalated`, `resolution_time`,
`tool_calls_per_ticket`, `ai_cost_per_ticket`, `approval_rate`,
`remediation_success_rate`, `repeat_incident_rate`.

This is the ROI story for sales/pilot conversations — treat it as a shipped
feature, not analytics bolted on later.

## Demo scenarios (must run 10/10 on multiple real Windows machines)

**A — Printer**
`ticket -> printer.status -> service.status -> [approval] -> service.restart -> printer.test -> resolved`

**B — DNS**
`ping gateway -> DNS lookup fails -> [approval] flush DNS -> DNS lookup succeeds -> resolved`

**C — Hung app**
`process.list -> app not responding -> [approval] -> process.kill -> user reopens / predefined app start -> verify process healthy`

**D — Disk full**
`disk.usage -> temp.scan -> show reclaimable (e.g. 14GB) -> [approval] -> temp.clean -> disk.usage -> resolved`

## Autonomy default: OFF for writes

v0.1 default: **read actions run automatically, every write action requires human
approval** — including `network.flush_dns`. Only after pilot data shows a tool is
safe (e.g. `service.restart: 99.4% safe`, `flush_dns: 99.9% safe`,
`temp.clean: 97.8% safe`) does a tenant get the option: *"Allow low-risk autonomous
remediation."* Default-off is a launch-safety decision, not a placeholder.

## Definition of Done — v0.1

1. Windows machine has the agent installed
2. Device enrolls securely
3. Dashboard shows online/offline
4. User creates a ticket
5. AI diagnoses using real tools (not guesses)
6. AI proposes remediation
7. User approves
8. Agent executes the action
9. Backend verifies via tool call (deterministic, per registry)
10. Ticket auto-closes on verified success
11. Full workflow is in the audit log
12. Technician can take over via MeshCentral on failure
13. Tenant/device kill switch works

If all 13 hold, v0.1 is done — ship it to pilot. Do not add browser automation,
CAD, or ads integrations before pilot feedback comes back.

## Product framing

Not "a platform that supports everything." It's an **AI Windows Support Agent with
remote-hands fallback** — small enough to finish, strong enough to prove the whole
thesis (AI can diagnose + fix real Windows problems safely, with verifiable proof
and a human escalation path when it can't).
