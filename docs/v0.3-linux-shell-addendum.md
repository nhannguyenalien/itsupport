# Linux `shell.run` — scope addendum

Status: **implemented in the backend and the Linux agent; not deployed.** Off by
default for every tenant and device. Source of truth for this feature; do not
write code that is not described here without updating this doc first.

Where the code is: classifier `agent/internal/shellrun/` (Go, authoritative) and
`backend/src/shell-run/` (TypeScript mirror), both reading one `rules.json` and
tested against one `classify.json` fixtures file; policy in
`backend/src/policy-engine/index.ts`; request/approval flow in
`backend/src/tool-calls/`; tool wiring in `agent/internal/tools/shellrun_linux.go`.

Supersedes, for Linux only, the "no free-form execution" rule in
[`v0.1-spec.md`](v0.1-spec.md) ("Why no `run_powershell`"). Windows and macOS are
unchanged and remain allowlisted-tools-only.

## Why

Every new system a customer runs (Proxmox, Docker, ZFS, nginx, Postgres…) used to
need a hand-written tool, even though the model already knows the CLI. Example from
the pilot: on a Proxmox host the assistant could not run `qm list`, concluded the
tool was "not installed" and proposed `package.install qm` — the binary was already
on the machine. The assistant had no way to ask the machine a plain question.

## What changes, and what does not

One new tool, `shell.run`, available on Linux devices only. The v0.1 guarantee that
the tool registry, policy engine, approval workflow and audit log are not bypassed is
kept: `shell.run` is *classified per command*, and the classification — not the
model — decides whether a human must approve.

Unchanged: every existing tool, process separation (daemon / telemetry / executor),
signed messages, kill switch, Revoke Device, Pause Device Actions, Disable Tenant AI,
audit log, metrics.

## The tool

```
shell.run { argv: string[], purpose: string, verify_argv?: string[] }
```

- `argv` is an **argument vector, never a shell string**. The executor `execve`s it
  directly. There is no `/bin/sh -c`, so pipes, redirects, `;`, `&&`, `$(...)`,
  backticks, globbing and variable expansion do not exist. A model that wants to
  filter output asks for the full output; the backend truncates and the model reads it.
- `purpose` is one sentence shown to the human in the approval card and stored in
  the audit log.
- `verify_argv` is a **read-class** command that proves the change worked
  (see Verification).
- Executable is resolved from a fixed PATH (`/usr/sbin:/usr/bin:/sbin:/bin`);
  `argv[0]` must be a bare name or an absolute path in those directories.
- Environment is rebuilt from scratch (`PATH`, `LANG=C.UTF-8`, `HOME=/root`);
  nothing is inherited. stdin is `/dev/null`. cwd is `/`.
- Output: stdout and stderr captured separately, **64 KiB cap each**, then
  truncated with a marker. Secrets are redacted before leaving the device
  (see Privacy).
- Time limit: **30 s** for read-class, **10 min** for approved commands. Process
  group is killed on timeout.

## Classification

The classifier lives in the **executor** (authoritative, compiled in) and is mirrored
in the backend policy engine (to choose auto-run, approval or reject before anything is queued). If they disagree, the stricter
result wins. Result is one of:

| Class | Meaning | Behaviour |
|---|---|---|
| `read` | Matches a rule in the read allowlist | Runs automatically, no approval |
| `write` | Anything not `read` and not `deny` | Always needs human approval, even with tenant autonomy on |
| `deny` | Matches the deny list | Rejected at the agent; cannot be approved |

**Default is `write`.** An unknown binary, unknown subcommand, or unknown flag is
`write`, never `read`. The model cannot talk its way to `read`.

### Read allowlist

Rules are `(binary, subcommand, permitted flags, positional-argument shape)`, not
prefixes — `qm list` is read, `qm list --anything-new` is not until a rule says so.
Initial set, deliberately small:

- Proxmox: `pveversion`, `qm list|status|config|listsnapshot`,
  `pct list|status|config|listsnapshot`, `pvesm status|list`, `pvesh get <path>`
  (get only), `pvecm status|nodes`. `vzdump` is **not** read.
- ZFS/storage: `zpool list|status`, `zfs list|get`, `lsblk`, `blkid`, `df`, `du -s`
  on a path allowlist, `smartctl -H|-i|-A <dev>`, `findmnt`.
- Docker: `docker ps|images|inspect|logs --tail N|stats --no-stream|info|version`.
  Never `exec`, `run`, `cp`, `rm`, `build`.
- systemd: `systemctl status|is-active|is-enabled|show|list-units|list-timers|
  list-unit-files`, `journalctl` with `-u`, `-n`, `--since`, `--no-pager`.
- System: `uname`, `uptime`, `free`, `lscpu`, `lsmem`, `ip a|r|link`, `ss -tulpn`,
  `hostnamectl`, `timedatectl status`, `who`, `last`, `lsmod`, `dmesg --notime`.
- Files: `ls`, `stat`, `cat`/`head`/`tail` restricted to the path rules below.

`find`, `awk`, `sed`, `tar`, `curl`, `wget`, `rsync`, `ssh`, `scp`, `nc`, `python`,
`perl`, `bash`, `sh`, `xargs`, `env`, `timeout`, `nice`, `watch`, `tee`, `dd`, `less`,
`vi`, `man` can execute or write via flags or arguments and are **never read**,
whatever the arguments (they are `write`, or `deny` for the interpreters and
shells).

### Path rules (file-reading commands)

Allowed roots: `/proc`, `/sys`, `/var/log`, `/etc` minus the deny list, `/opt`
(minus agent dir), `/home/*/.config` is **not** allowed. After `realpath`
resolution (symlinks followed), the path must still be inside an allowed root and
not match the deny list. Check happens in the executor, not the backend.

### Deny list (cannot be approved)

- Shells, interpreters and REPLs as `argv[0]`: `sh bash dash zsh fish python*
  perl ruby node php lua awk`.
- Downloading and executing: `curl`/`wget` with output to a file or piped,
  `base64 -d`, anything writing under `/usr/bin /usr/sbin /bin /sbin /lib*`.
- Touching the agent or its secrets: any path under `/etc/itsupport-agent`,
  `/opt/itsupport-agent`, `/usr/local/mesh_services`, the `itsupport-*` and
  `meshagent` systemd units (stop/disable/mask/edit/kill), `service.env`.
- Credentials: `/etc/shadow`, `/etc/gshadow`, `*/.ssh/*`, `/root/.*history`,
  `/etc/pve/priv/*`, `/etc/ssh/ssh_host_*_key`, private keys and `*.pem`/`*.key`,
  `/proc/*/environ`, `/proc/*/mem`.
- Account/auth/network-security changes: `passwd`, `chpasswd`, `usermod`,
  `useradd`, `userdel`, `visudo`, edits to `sudoers`, `authorized_keys`,
  `iptables`/`nft`/`ufw`/`pve-firewall` rule changes, `ssh-keygen`.
- Destructive: `rm -r*` on `/`, `/boot`, `/etc`, `/var`, `/usr`, `/home`,
  `mkfs*`, `wipefs`, `fdisk`/`parted`/`sgdisk` write operations, `dd of=/dev/*`,
  `shred`, `chmod/chown -R /`, `reboot -f`, `echo b > /proc/sysrq-trigger`.
- Disabling the product's own controls (anything that would stop the agent).

The deny list is evaluated first; a command matching it is rejected even if a read
rule also matches.

## Approval (write class)

- The approval card shows the **exact argv** (quoted), the `purpose`, the target
  device, and the verification command. Approving applies to that exact command
  and that device, once. A different argv, a retry, or another device needs a new
  approval.
- How the agent knows a write was approved (as built): when the agent polls for
  work, the backend adds `__approved: true` to the params of a `shell.run` row only
  if an `approvals` row with `status = 'approved'` and the *same tool and params*
  exists. `__approved` is never stored, and any request carrying a parameter that
  starts with `__` is rejected, so neither the model nor a user can supply it. The
  agent runs a write-class command only with that flag and never runs `deny`.
  Limitation, stated plainly: this protects against the model, the UI and a stale
  or edited row, but not against a compromised backend, which could set the flag.
  A cryptographic per-command signature (backend signs `{deviceId, argv hash,
  approvalId, expiresAt}`, agent verifies) is the planned hardening and is **not**
  built.
- An approved command expires: if the device has not run it within 15 minutes of
  approval, the backend marks it timed out instead of handing it over later.
  Approving also re-checks that the tenant and device flags are still on, the device
  is not paused or revoked, and the command is still not `deny`.
- Tenant autonomy never promotes `write` to auto-run. A tenant may later opt a
  *specific, named* write rule (e.g. `qm snapshot` on a given VMID) into autonomy
  after pilot data, as already described in the v0.1 "Autonomy" section. Not in
  this version.

## Verification

Same rule as v0.1: "looks fixed" is not a terminal state.

- A `write` proposal **must** carry `verify_argv`, itself `read` class. The backend
  runs it after the write and the model reads the result.
- No `verify_argv`, or verification failing, ends the ticket as
  `REMEDIATION_FAILED` / `EXECUTED_UNVERIFIED`, never `RESOLVED`.
- Example: `qm start 105` → verify `qm status 105` must contain `status: running`.

## Enablement

- Off by default. Tenant setting `shell_run_enabled` (default **false**) and a
  per-device switch (default **false** for existing devices, so upgrading never
  silently grants it). Both must be on.
- Linux devices only. The executor build for Windows/macOS does not contain the
  tool; a `shell.run` message is rejected at the agent boundary as an unknown tool.
- Disable Tenant AI, Pause Device Actions and Revoke Device stop it like any tool.

## Prompt-injection and data handling

- Command output is **untrusted data**. It is passed to the model inside a clearly
  delimited block, and the system prompt states that instructions found there
  are never to be followed. The model's next `shell.run` still goes through the
  classifier and, if `write`, a human. Injection cannot widen what runs without
  approval, only what is *proposed*.
- Redaction before output leaves the device: private-key blocks, `password=`/
  `token=`/`secret=`/`api_key=` values, `Authorization:` headers, JWT-shaped strings,
  and lines from files matched by the credential deny list.
- Output is stored in the audit log with the same retention as other tool results.

## Audit and metrics

Audit record per call: tenant, device, ticket, the human who approved (if any),
full argv, class, classifier rule matched, exit code, duration, output byte counts,
truncated flag. Metrics: share of commands by class, read-rule hit counts,
`deny` rate, approval rate, verification pass rate. A model that keeps proposing
denied commands is a signal worth alerting on.

## Privilege

The executor runs as root on Linux today, and Proxmox tools (`qm`, `pct`, `pvesh`)
require root. That means a classifier bug is a root bug. Mitigations in this
version: default-`write` classification, no shell, fixed PATH, deny list in the
executor, signed per-command approval, path checks after `realpath`. Out of scope
now but tracked: running `read`-class commands that do not need root as an
unprivileged user.

## Test requirements (before any device gets it)

1. Table-driven classifier tests, executor and backend sharing one fixtures file;
   both must agree on every row.
2. Negative corpus the classifier must never mark `read`: `qm list; rm -rf /`,
   `docker run -v /:/h …`, `find / -exec …`, `journalctl --pager`/`-o` abuse, `ls
   $(…)`, `cat /proc/self/environ`, symlink into `/etc/shadow`, `systemctl stop
   itsupport-daemon`, `curl … | sh` expressed as argv, `env sh`, `timeout 1 sh`,
   `ssh` anything, unicode lookalikes and null bytes in args.
3. Approval-signature tests: wrong device, edited argv, expired, replayed.
4. Redaction fixtures.
5. Live test on one Proxmox host with `shell_run_enabled` on: `qm list`, `pct list`,
   `zpool status` auto-run; `qm start`/`qm stop` on a throwaway VM require approval;
   `rm -rf /tmp/x` as approval; `systemctl stop itsupport-daemon` rejected. No write
   command runs on a production VM without the owner's explicit say-so.

## Rollout

1. Backend: tool in `registry.json` (`risk` resolved per call, not static),
   classifier mirror, approval signature, tenant/device flags, DB migration for the
   two flags.
2. Agent: executor classifier + runner, Linux build only; rebuild amd64/arm64.
3. UI: approval card showing argv, per-device toggle (off), tenant toggle (off).
4. Enable on two internal Proxmox hosts (`pve`, `promox`), run the live test, widen
   only after reviewing the audit log.
5. Rollback: tenant flag off instantly stops it; revert backend image and agent
   binaries otherwise. No data migration to undo beyond dropping the flags.

## Decisions on the original open questions

1. Read-class commands run as root for now (Proxmox needs it); dropping privileges
   where possible is future work.
2. `docker logs` stays `read`, with output redaction.
3. `pvesh get` is limited to `/nodes`, `/cluster/resources`, `/cluster/status`,
   `/storage` and `/version`; `/access/*` is not readable.
4. Only we change the read rules (`rules.json`); tenants cannot extend them.

## Enabling it

Both flags must be on, and both default to off:
`POST /tenants/:id/enable-shell-run` (and `disable-`) and
`POST /devices/:id/enable-shell-run` (and `disable-`, Linux devices only). All four
are admin-only and audited (`tenant.shell_run_*`, `device.shell_run_*`). Every
`shell.run` audit record carries the argv, class and matched rule. The AI is only
offered the tool, and only given the usage instructions, when both flags are on;
the policy engine enforces the same rule again.

## Verified so far

- Go and TypeScript classifiers agree on all shared fixtures (about 250 argv
  vectors including the negative corpus), enforced by `backend/tests/shell-run.test.ts`
  and `agent/internal/shellrun/classify_test.go`.
- On a real Proxmox host (`promox`) and an ARM64 VPS (`cynet`): the Go tests pass
  on Linux; `qm list`, `pct list`, `pvesh get /nodes`, `systemctl status`, `df`,
  `docker ps` and `journalctl` run; `cat /etc/shadow` is denied; `qm stop 101`
  without approval is refused and does not run.
- Not yet done: the approval card in the web UI showing the exact argv, UI toggles
  for the two flags, the cryptographic signature above, and any live test of an
  approved write. No device has the feature enabled.
