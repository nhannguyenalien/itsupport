# Computer-use addendum — AI remote desktop assist

Added after v0.1 spec lock, at explicit user request (2026-09-13). Both
[`v0.1-spec.md`](v0.1-spec.md)'s "Why no `run_powershell`" section and
[`v0.2-marketing-ops-spec.md`](v0.2-marketing-ops-spec.md) call Computer Use
**out of scope** — this doc is the required scope update before implementing
it (repo convention: "do not expand scope without updating this doc first").

## What this is

The AI can see a customer's actual desktop (screenshot) and propose
mouse/keyboard actions (click, double-click, drag, keypress, type, scroll,
move, wait) via OpenAI's Responses API `computer` tool
(`backend/src/computer-use/index.ts`, model `gpt-5.6-sol` by default). For
diagnoses the fixed 16-tool registry can't reach — an unfamiliar third-party
app's UI, a one-off dialog — this lets the AI act instead of only being able
to describe what a human should click.

## Why this doesn't reopen the "no `run_powershell`" hole

The v0.1 spec's core security argument is: if the agent accepts arbitrary
instructions, the Tool Registry / Policy Engine / Approval workflow are
theater. Computer-use control is real reach into the machine, so it earns the
same scrutiny — three things keep it inside that model rather than around it:

1. **Fixed action taxonomy, not arbitrary code.** The agent exposes exactly 9
   compiled Go functions (`agent/internal/tools/desktop_windows.go`) —
   click/double_click/drag/keypress/move/scroll/type/wait/screenshot — through
   the same compile-time allowlist (`KnownTools`/`Allowlist`) every other tool
   uses. There is no "run this script" or "type any command" primitive; typing
   arbitrary text still only ever calls `SendInput`, never a shell.
2. **Every write action requires human approval, unconditionally.** In
   `registry.json`, `desktop.click/double_click/drag/keypress/type/scroll` are
   `risk: "high"` — `policy-engine/index.ts` never auto-executes `high` risk
   regardless of a tenant's autonomy opt-in (only `low` can, and only with that
   opt-in). This is a deliberate, explicit user requirement, not an inferred
   default: no session-level blanket approval exists in this build. Only
   `desktop.screenshot`/`move`/`wait` are `risk: "read"` (no device-state
   change) and auto-execute, same as any other read tool.
3. **Independent re-validation at the agent, like every other tool.**
   `desktop_windows.go` re-clamps coordinates against the real screen bounds,
   allowlists key names (an unrecognized key name is a hard error, not a
   guess), and caps typed-text length and drag-path/keypress-chord size — the
   same defense-in-depth principle `browser_windows.go`'s `OpenURL` already
   established (never trust that upstream validation already happened).

## Real API verification (2026-09-14) — and a mid-flight API migration

This feature was originally built against `computer_use_preview`
(model `computer-use-preview`), the tool/model available when this addendum
was first written. Testing against the real OpenAI API with a real key
confirmed that model is **retired**: `404 The model computer-use-preview does
not exist or you do not have access to it`. OpenAI's current docs point at a
replacement — tool type `"computer"`, model `gpt-5.6-sol` — which this build
now uses (`OPENAI_COMPUTER_USE_MODEL` still the env var, default changed).

The migration wasn't a find-and-replace: the current `computer` tool returns
**batched** `actions[]` per `computer_call` (one shared `call_id`, one
`pending_safety_checks` for the whole batch) instead of one `action` at a
time. That's a real conflict with this feature's hard requirement — every
single action needs its own human approval — so `computer-use/index.ts`
(`dispatchAction`) walks a batch one action at a time: each action still gets
its own approval/execution/verification exactly like before, and the model is
only called again once every action in the batch has resolved, at which point
one end-of-batch screenshot and one `computer_call_output` (the shared
`call_id`, the batch's `acknowledged_safety_checks`) goes back. A single
`action` response is treated as a batch of one, so the common case is
unchanged in practice. Verified against a local mock server asserting: (a) a
2-action batch produces exactly 2 separate approvals before the mock is ever
called a second time, (b) the second action dispatches with no additional
model call, (c) the end-of-batch response carries the correct shared
`call_id` and the batch's actual safety checks (an earlier draft of this fix
had a bug here — it echoed the last individual action's empty per-action
safety-check stash instead of the batch's real one; caught by the mock
assertion before it shipped).

Also found and fixed during real-API testing (affects the *regular* ai-step
tool-calling loop too, not just computer-use): OpenAI function-calling names
must match `^[a-zA-Z0-9_-]+$` — this repo's dotted tool names
(`service.status`) were rejected outright the moment more than one tool was
offered (`400 Invalid 'tools[0].function.name'`). This had never surfaced
before because nothing had been tested against the real API prior to this
session — mocks and typechecking don't catch a real API's validation rules.
Fixed in `backend/src/ai-orchestration/schema.ts` via a reversible `.`↔`-`
substitution (`toOpenAiToolName`/`fromOpenAiToolName`; confirmed no tool name
in `registry.json` already contains a hyphen, so the mapping is unambiguous).
Confirmed working end-to-end afterward: `gpt-4.1-mini`, given a ticket titled
"Printer PR-201 wont print, spooler seems stuck", correctly chose
`service.status(spooler)` as its first diagnostic step.

## Autonomous mode with technician fallback (added 2026-09-14)

Per-action approval (§ above) is still the default. A tenant can opt into
**autonomous computer-use** — the AI drives click/type/etc. without pausing
for a human on every action, with a technician stepping in only when the AI
can't finish — via `tenants.computer_use_autonomous_enabled` (no UI toggle
yet, same as `autonomous_low_risk_enabled`; set directly in the DB). This is
a **separate** flag from `autonomous_low_risk_enabled` — that one only ever
unlocks `risk:"low"` IT tools; computer-use writes stay `risk:"high"` by
design, so this needed its own opt-in (`policy-engine/index.ts`).

**What stays hard-blocked even in autonomous mode** — and what genuinely
can't be, flagged not hidden:
- **Payment card numbers**: `desktop.type` text is checked against a Luhn
  checksum (`backend/src/policy-engine/luhn.ts`) for any embedded 13-19-digit
  card-number pattern; a match always forces approval, unconditionally. This
  is the *only* reliably detectable signal — OpenAI's computer-use actions
  carry coordinates or literal typed text, never semantic context like "this
  is a password field," so a click into a sensitive field (before anything
  is typed) is undetectable by design. Not a gap left for later — there's no
  data available at this layer to close it with.
- **Delete/uninstall**: **not** a hard technical block, by necessity — those
  are just ordinary clicks/keypresses (e.g. the Delete key, used constantly
  for routine text editing) with no structural "this is destructive" marker;
  hard-blocking every Delete keypress would make "autonomous" meaningless.
  Instead this is a **prompt-level instruction only**
  (`computer-use/index.ts`'s first-call prompt tells the model to always
  pause and explain before anything irreversible) — a nudge, not an
  enforcement mechanism.

**Fallback trigger**: the model's own final message must be prefixed
`RESOLVED:` or `ESCALATE:` — enforced by `advanceSession()`, not left to free-
text parsing. `RESOLVED:` ends the session cleanly. `ESCALATE:` — or any final
message matching neither prefix, treated as an implicit escalate, since an
ambiguous ending must never read as success — ends the session **and** flips
`tickets.status` to `'escalated'` (`endSession()`, which now also handles
this for every other automatic session-ending path: verification failure,
device-reported execution failure, or a rejected approval for the payment
hard-block). Verified against a scripted mock: a click auto-executed with no
approval row; a card-number `desktop.type` still created one despite
autonomous mode; an `ESCALATE:` message flipped the ticket to `'escalated'`
with a clear audit trail; a `RESOLVED:` message left the ticket untouched.

## Customer-facing status/chat view (added 2026-09-15)

Every chat/approval UI up to this point (`frontend/src/app/tickets/[id]/page.tsx`)
is technician-facing — the customer whose machine is being controlled had no
visibility at all. `startSession()` (`backend/src/computer-use/index.ts`) now
also requests a new tool, `desktop.open_customer_view` (`risk:"read"`,
`domain:"windows_desktop"`, `registry.json`), right after the initial
screenshot — **system-triggered only**, excluded from the regular
ai-orchestration tool list the same way every other `windows_desktop` tool
is, since the AI must never decide to call this itself.

The tool opens the customer's own default browser to a **separate** page,
`frontend/src/app/tickets/[id]/customer/page.tsx` — not a stripped-down mode
of the technician page, a genuinely different one — reading the same `GET
/tickets/:id` and posting to the same `POST /tickets/:id/messages`
(`authorType:"user"`, the same author type the technician page's own chat box
already used for customer-attributed messages) but showing only: the ticket
title, one plain-English "what's happening now" sentence (no tool names, no
JSON — derived client-side from `toolCalls`/`approvals`/`status`), the full
chat log, and a send box. No Approve/Reject controls, no `RiskBadge`, no raw
params — those stay technician-only, on the other page. The shared root
layout's nav bar (`frontend/src/app/TopNav.tsx`) also hides itself on this
route so a customer's browser tab never surfaces links into the internal
dashboard.

**Where the URL comes from**: same never-trust-the-caller principle as
`browser.open_url` — `tool-calls/service.ts` computes
`${FRONTEND_URL}/tickets/:id/customer` server-side (new env var
`FRONTEND_URL`, default `http://localhost:3001`) and the agent independently
re-validates it before opening anything (`agent/internal/tools/customerview.go`'s
`validateCustomerViewURL` — http or https, and the path must match
`/tickets/<uuid>/customer` exactly), same defense-in-depth shape as every
other agent tool. Implemented for all three OSes
(`customerview_{windows,darwin,linux}.go`: `cmd /c start`, `open`, `xdg-open`
respectively) and verified for real: starting a session against a local
Postgres queued both the screenshot and this tool with the correct URL, and
the customer page — opened for real in a browser — rendered the friendly
status line, accepted a typed message, and that message showed up via the
backend's own `GET /tickets/:id` with `author_type:"user"`, exactly as a
technician would see it on their side. The actual browser-launch step
(`OpenCustomerView` itself) is compile/vet-verified only, same "not live-
tested" honesty already applied to `browser.open_url`.

**What this is not**: a consent gate — see the known-gaps entry below.

## Known gaps — flagged, not hidden

- **No on-device *consent* for the customer whose machine it is** (partially
  addressed — see "Customer-facing status/chat view" below for the
  *visibility* half). A customer's browser now auto-opens to a status/chat
  page (`desktop.open_customer_view`) the moment a session starts, so they
  can see what's happening and message the technician — but that's a notice,
  not a consent gate: the AI is already acting by the time the page opens,
  there's no "allow this session?" prompt the customer must accept first,
  and nothing stops them from simply not looking at the browser tab that
  opened. A real consent gate would mean pausing the very first action until
  the customer acknowledges the page — not built.
- **No pixel-level screenshot redaction.** `docs/v0.1-spec.md`'s data-privacy
  pipeline (filter → redact → LLM) works on structured text; there's no
  equivalent for arbitrary screen pixels (a password manager popup, an open
  email). Mitigation, not a fix: `policy-engine/index.ts` rejects every
  `domain: "windows_desktop"` tool outright for a tenant on
  `ai_data_policy = 'no_screenshots'` — those tenants can't start a session at
  all. Tenants on `standard`/`redacted`/`no_raw_logs` get no screenshot
  redaction whatsoever; this needs a real answer (blur/OCR-redact, or an
  explicit customer consent step per session) before a pilot with real
  customer machines, not just before GA.
- **No Windows runtime testing.** Same limitation the README already states
  for the original 16 tools — this dev environment has no Windows box. The
  `SendInput`/`GetDIBits`/coordinate-normalization code in
  `desktop_windows.go` is compile-verified (`GOOS=windows go build`) and its
  pure bounds math is unit-tested (`bounds_test.go`), but the actual Win32
  struct layouts and multi-monitor coordinate math are unverified until tried
  on a real machine.
- **A rejected action ends the session, not a retry loop.** If a technician
  rejects a proposed click/type, v0.1 posts a message and ends the session
  rather than telling the model to try something else — simpler and safer for
  a first pass, but means one rejection restarts the whole diagnostic context.
- **Session state is not queryable after a page reload.** `computer_use_sessions`
  exists in the DB, but there's no `GET /tickets/:id/computer-use` to resume
  tracking an in-progress session from the frontend — reloading the ticket
  page loses the local "which session am I watching" state (the backend state
  itself is intact; a resume endpoint is unbuilt).

## Multi-OS support (added 2026-09-14)

Originally Windows-only, like the rest of the agent. Extended after the user
asked whether other OSes, mobile, and TV platforms are supported.

**macOS — real implementation.** `agent/internal/tools/desktop_darwin.go`:
`DesktopScreenshot` shells out to the OS's own `/usr/sbin/screencapture`
(no cgo); every input-injection tool (`click`/`double_click`/`drag`/
`keypress`/`type`/`scroll`/`move`) uses cgo bindings to Quartz Event Services
(`CGEventPost`). Built and unit-tested for real on this project's own dev
machine (darwin/arm64) — `go build`/`go vet`/`go test` all actually compile
and link the cgo code here, not just cross-compile-check it. Known
simplifications: bounds-checks only the **main** display (a click/type
targeting a secondary display on a multi-monitor Mac is rejected as
out-of-bounds); `desktop.keypress` assumes a US ANSI keyboard layout
(`desktop.type`, which posts Unicode directly, has no such limitation); mouse
`button: "back"/"forward"` isn't supported (Quartz has no equivalent).

**macOS — general IT-diagnosis tools (added 2026-09-15).** Three of the
original 16 Windows-only tools were ported for real dogfooding on this
project's own dev machine: `disk.usage` (`disk_darwin.go`, `statfs(2)`),
`process.list` (`process_darwin.go`, shells out to a fixed, parameterless
`ps -axo pid=,ppid=,comm=` — no caller input ever reaches the command line,
same principle as `screencapture`/`open` elsewhere in this file set), and
`temp.scan` (`temp_darwin.go`, pure Go `os`/`filepath`, scoped to `$TMPDIR`
and `/tmp` only). Deliberately **read-only** — `service.status`, `printer.*`,
`temp.clean`, and the rest of the original 16 remain Windows-only; this pass
only covers what's needed to actually run a real diagnosis on a Mac.
Verified two ways: called directly against this machine (`disk.usage`
correctly reported 93% full / 15.95GB free out of 228GB, `process.list`
returned 599 real processes headed by `launchd`, `temp.scan` found 192.86MB
across 3525 files in `$TMPDIR`), and through the *actual product loop* —
a real ticket ("This Mac is almost out of disk space"), real `gpt-4.1-mini`
calls via `POST /tickets/:id/ai-step`, real tool results fed back in. The
model correctly chose `system.info` first (not ported — got back an honest
"not wired in this build" error, exactly as a real agent would report),
recovered by trying `disk.usage`, read the real 93%-full number correctly,
proposed `temp.scan` next (matching the spec's own Scenario D shape), and
concluded correctly that 192MB of reclaimable temp files "could free up some
space" without overselling it as a fix for a 93%-full disk.

**Linux (X11) — scaffold, not verified.** `agent/internal/tools/desktop_linux.go`
uses `github.com/BurntSushi/xgb` (a pure-Go X11 protocol client — no cgo, so
it cross-compiles from any dev machine) and the XTEST extension. This has
**never been run against a live X server** — there's no Linux box in this
project's dev environment, so `go build`/`go vet` for `GOOS=linux` are the
only checks that have ever touched it. Explicitly out: Wayland (compositors
generally refuse synthetic input/screen capture from an unprivileged client —
no portable fix); the screenshot code assumes a 32bpp BGRX visual (the common
case, but unverified); typed text is limited to the printable ASCII range
resolvable through the X server's *current* keyboard mapping (no dynamic
remapping for characters the active layout doesn't expose anywhere).

**Mobile (iOS/Android) and TV OSes (tvOS, Android TV, webOS, Tizen, ...) —
not attempted.** These are platform-level walls, not a missing-code gap:
- **iOS**: no generic third-party API for an app to capture the whole screen
  and inject touch input system-wide; the real mechanisms (enterprise MDM,
  or the vendor-specific "remote assistance" APIs Apple grants to select
  partners) are outside what a third-party product can build into itself.
- **Android**: possible in principle, but requires a wholly separate native
  Android app (Kotlin/Java, not this Go codebase) using AccessibilityService
  + MediaProjection, with the user manually granting both permissions in
  Settings — and Google Play reviews "remote control" behavior heavily. Not
  started.
- **TV OSes**: essentially no third-party screen-capture/input-injection API
  exists on any of them — not a gap to close, a wall to route around (e.g.
  the existing MeshCentral human-takeover path, which doesn't depend on this
  agent at all).

`devices.platform` (`'windows'|'mac'|'linux'`, set by `cmd/enroll` from
`runtime.GOOS` at enrollment) is passed as-is into the first-call prompt text
naming the environment being controlled — the current `computer` tool (unlike
the retired `computer_use_preview` one) takes no `environment` field itself,
so this moved from a structured API field to plain prompt text. Nothing in
`registry.json` or `policy-engine/index.ts` needed to change for multi-OS,
since a tool's risk level and approval requirement were already
platform-agnostic. Verified for real: macOS screenshot capture tested on this
project's own dev machine, and Linux/X11 screenshot capture tested against a
real X server on a real Linux machine reached over SSH (`ssh mac@macmini`) —
both captured and decoded a real image. Click/type/etc. injection has only
been exercised through the mock server on both platforms, not live.

## What's unchanged

Approval UI, audit log, verification chain, kill switches (tenant AI
disable, device pause) — all identical to every other tool call. This
addendum adds tools and one new orchestration loop; it does not touch the
policy engine's decision logic beyond the two additions above (`no_screenshots`
gate, `windows_desktop` exclusion from the regular chat-completions tool list).
